# Build Plan

List the features that make up your project, high level and in rough build order.
Keep each item to one line; the details come later in `/feature`.

Run `/feature` to spec the next unchecked item, or `/feature 2` to pick one.
Keep completed items checked and append new features as the project grows.
Do not renumber completed features; their archived specs refer to those IDs.

## Your features

- [x] 1. **Browse offers (home page)** - fetches and lists offers from the API, client-side sorted by date, but reads legacy field names (`product_image`, `product_price`, `product_details` as an array) that no longer match the live backend's flat `image`/`price`/`details` contract; needs rework alongside item 7.
- [x] 2. **Offer detail page** - shows a single offer's image, price, details, and seller, but has the same legacy field-name mismatch (`product_name`, `product_description`, `product_image`, `product_details` array) as item 1; needs rework alongside item 7.
- [x] 3. **Signup** - form exists, but posts to the old `/user/signup` route (404 against the live backend, which is `/users/signup`) and reads a `token` field the backend no longer returns (it returns `accessToken`); rebuild alongside items 7-8. Done: the route/field fix landed with item 8's migration (`01c18f5`), and item 12 added the confirmation-message UX on top.
- [x] 4. **Login** - form exists, but has the same obsolete route (`/user/login` vs `/users/login`) and `token`/`accessToken` mismatch as signup, and doesn't handle the backend's real 403 (invalid credentials or unconfirmed account) and 423 (locked account) responses; rebuild alongside items 7-8. Done: the route/field fix landed with item 8's migration, and item 9 added the 403/423 handling.
- [x] 5. **Publish an offer** - form with a single image upload; the route and required fields (`title`, `description`, `price`, `brand`, `size`, `color`, `condition`, `city`, `picture`) already match the live backend. Only missing multi-image (`pictures`) support and post-success feedback, covered by item 20 (previously mis-referenced as item 19).
- [ ] 6. **Real Stripe checkout** - > TODO (confirm): `CheckoutForm.jsx` currently posts to an unrelated external Le Reacteur endpoint, not `vinted-backend`, which has no payment route at all today. The real flow needs Stripe products/prices and a webhook created in the Stripe dashboard, plus a payment route added to `vinted-backend` (create a PaymentIntent, verify the webhook, update the offer's status). Scope the frontend wiring once that backend work starts.
- [x] 7. **Environment variables + generic error component** - point `VITE_API_URL` at the new backend routes, move the hard-coded Stripe publishable key into env, and add a shared error-display component so forms stop duplicating `error.response?.data?.message` (and stop breaking when `error.response` is undefined).
- [x] 8. **Migrate to `/users/*` routes and new offer field names** - update all API calls to the renamed user routes (`/users/login`, `/users/signup`, plus `confirm`, `reset`, `favorites`, etc.) and the new offer response shape (`name`, `description`, `price`, `details` as a flat object, `image`, `pictures`). Delete the now-unnecessary `productDetails` array-reconstruction logic in Home and Offer rather than adapting it.
- [x] 9. **Login: new token flow + account-state errors** - switch to an in-memory JWT access token plus the backend's httpOnly refresh cookie; handle 403 (unconfirmed account, offer to resend the confirmation email) and 423 (account locked after 5 failed attempts, show the 15-minute lockout message). Every authenticated axios call must set `withCredentials: true`, since the backend restricts CORS to `origin: FRONTEND_URL, credentials: true` and the refresh cookie is scoped `path: /users` - without it the cookie never reaches or leaves the backend cross-origin.
- [x] 10. **Silent token refresh** - cross-cutting request logic: on a 401 from any authenticated request, attempt a refresh, replay the original request, and only redirect to `/login` if the refresh also fails. Also needs `withCredentials: true` (see item 9) so the refresh cookie round-trips.
- [x] 11. **Logout: invalidate session server-side** - today `Header.jsx` only clears the local cookie via `handleToken(null)`; add the `POST /users/logout` call to also end the session on the backend.
- [x] 12. **Signup: handle inactive-account response** - on 201, show a "check your email" message instead of redirecting straight to Home, since login is refused until the account is confirmed.
- [x] 13. **Account confirmation screen** - new `/confirm/:token` route that calls `GET /users/confirm/:token` on load and shows activated vs. invalid/expired, with a link to resend.
- [x] 14. **Resend confirmation email** - small email-only form (`POST /users/confirm/resend`), reachable from login and from the failed-confirmation screen; the backend response is the same either way, so the UI just confirms it was sent.
- [x] 15. **Forgot password flow** - request screen (`POST /users/reset/request`, email only) and confirm screen (`POST /users/reset/confirm`, code + new password), with a "Forgot password?" link on Login.
- [x] 16. **Consistent loading/error states** - every page that fetches (list, detail, favorites, my offers) must resolve to a real error state on failure instead of a spinner stuck forever.
- [x] 17. **Search, filters, sort, and pagination on the offers list** - wire the existing Header search input to `?title=`; add price-range filters (`?priceMin=&priceMax=`) and server-side sort (`?sort=price-asc|price-desc`) in place of the current client-side date sort; add pagination (`?page=`, 20/page, using the `count`/`page`/`totalPages` response).
- [x] 18. **Offer status on the detail page** - show a "Sold"/"Reserved" badge and disable the Buy button when the offer isn't `available`.
- [x] 19. **Multi-image gallery on the detail page** - display the secondary `pictures` (up to 5) alongside the main image.
- [x] 20. **Multi-image publish + success feedback** - support the required main `picture` plus up to 5 secondary `pictures`; on success, show a confirmation and redirect to the new offer instead of only logging to the console.
- [x] 21. **Favorites toggle** - heart/star on the offer card and detail page, using optimistic `POST`/`DELETE /users/:id/favorites/:offerId`; hidden or disabled when logged out.
- [ ] 22. **My Favorites page** - new `/favorites` route, authenticated-only, reusing the offer card to show `GET /users/:id/favorites`. Build item 28 first: without a session bootstrap, this page is signed-out and empty on every direct open, reload, or bookmark, which is exactly how an authenticated-only page gets reached.
- [ ] 23. **Edit, delete, and status changes for owned offers** - edit form (`PUT`/`PATCH /offers/:id`) pre-filled from the existing offer and reusing the publish form; status change (`PATCH /offers/:id`); delete (`DELETE /offers/:id`) with confirmation. Visible only to the offer's owner.
- [ ] 24. **Account profile page** - view/edit the connected user's profile (`PUT`/`PATCH /users/:id`: username, avatar upload, newsletter) and delete the account (`DELETE /users/:id`) behind an explicit confirmation, since it cascades to deleting all of that user's offers on the backend. Note: the backend has no "change password while logged in" route yet - only the forgot-password reset flow changes a password; flag this if an in-profile password change is actually wanted, since it would need a backend addition.
- [ ] 25. **Public seller profile page** - new `/users/:id` route (no auth required) showing a seller's username and avatar, linked from their name on an offer.
- [ ] 26. **"My offers" page** - > TODO (confirm): needs scoping before implementation. There is no dedicated backend route for a user's own offers yet; filtering the paginated `GET /offers` client-side would be fragile. The clean option is adding an `owner` filter on `GET /offers` or a `GET /users/:id/offers` route on `vinted-backend` first.
- [ ] 27. **Wire owner actions into "My offers"** - once feature 26 has a backend route, surface the edit/delete/status actions from feature 23 directly on each of the user's own offers in that page.
- [x] 28. **Restore the session on page load** - the access token lives only in `src/api/client.js` memory, so today any reload, shared link, or bookmark starts signed out: the Header offers "Se connecter" to someone who never logged out, and every authenticated affordance vanishes (verified during feature 21's `/check`: the favorite hearts are absent on a directly opened offer page). Attempt one `POST /users/refresh` when `App` mounts and adopt the returned `accessToken` when the httpOnly refresh cookie is still valid (verified live: the cookie is scoped `path: /users`, lasts ~30 days, and returns `{ accessToken }` on its own with no Authorization header). Treat a 401 as "genuinely signed out" and render normally, never a redirect to `/login`, since anonymous browsing is the app's default state. Hold the first render, or accept a brief signed-out flash, but decide which and say so; and note that `/users/refresh` returns no `_id`, so `getUserId()` keeps reading the token's `sub` claim. Build this before item 22, which is authenticated-only and otherwise opens empty every time. One trap this feature arms, raised by feature 21's independent review and unreachable until now: `useFavorites` keeps its favorites Set when `userId` changes while a page stays mounted, because its effect only refetches and never resets. Today every account change passes through `/login`, which unmounts `Home` and `Offer`, so the stale Set can never be seen. This item is the first thing that makes a session appear or change under an already-mounted page, so re-check it then: a Set carried across users would show one account's favorites to another. The fix is one line, clearing the Set when `userId` changes, but it only becomes necessary once the session can change without a remount.
